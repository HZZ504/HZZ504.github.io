今日焦点一：「Fable 5.1 52 分钟烧光配额」结案 —— 官方 changelog 承认了那个缓存 bug

回顾一下这个故事的三天：

日期 事件
9/1 Fable 5.1 发布（claude-fable-5-1），1M 上下文，缓存读取 $0.25/Mtok，官方口径「典型负载省 25%、智能体负载省 45%」
9/2 X 出现趋势话题：有人一条提示词跑完 20x Max 的 5 小时配额（52 分钟），另一些人4 分钟触顶；社区猜测「指向密集的缓存活动」
9/3 本报告写「降价与烧额度不矛盾，是计费口径不同」——这个解释只对了一半
9/4（今天） 2.1.260 changelog 直接写明这是 bug

原文一句话，值得逐字读：

> "Fixed prompt caching on Claude Fable 5.1 not covering the context attached after tool results, so it was re-sent as uncached input on every tool-call turn."

> —— Claude Code changelog 2.1.260

翻译成人话： 你每调用一次工具，工具结果之后挂上去的那部分上下文全部按未缓存输入重新计费。Claude Code 是一个每轮都在调工具的智能体——读文件、跑 bash、grep、编辑——所以这个 bug 的放大倍数正好等于你这一轮的工具调用密度。

这就解释了为什么「52 分钟烧光」和「省 45%」能同时是真的：

  • 省 45% 是缓存正常工作时的账
  • 52 分钟烧光 是缓存根本没工作时的账
  • 而智能体负载恰恰是两种情况下差距最大的那一类负载

同一版还配了第二条相关修复：

> "Improved /effort on Claude Fable 5.1 so changing effort mid-session no longer invalidates the prompt cache."

注意这条的讽刺意味： 9/2 社区给出的应对办法是「调低 effort 档位」。而在 2.1.260 之前，每调一次 effort 就砸掉一次缓存——也就是说，社区自救的动作本身，在当时又给账单加了一刀。

📌 今天就能做的一件事： 如果你在用 Fable 5.1 并且觉得额度掉得离谱，先 claude --version。低于 2.1.260 的，升级；升级前不要靠反复切 effort 来省钱。

今日焦点二：/cost 现在会告诉你「缓存为什么没命中」—— CLI 和 API 两条线终于对上了

2.1.260 加的这条，是过去半年 Claude Code 在可观测性上最实用的一次改动：

> "Added a likely cause for prompt-cache misses (e.g. tool definitions or system prompt changed, idle past the TTL) to /cost and the status line's prompt_cache field."

以前缓存没命中，你唯一的信号是 cache_read_input_tokens 变成 0，没有任何线索告诉你是哪一段变了。现在 /cost 直接给原因。

而这不是孤立的一条 —— 它和 API 侧的 Cache diagnostics（beta） 是同一套诊断逻辑的两个出口。官方文档对问题的描述几乎是同一句话：

> "A reordered tool, a timestamp interpolated into your system prompt, or an edit to an earlier message can silently invalidate the cache. Without cache diagnostics, the only signal is usage.cache_read_input_tokens dropping to zero, with no indication of what changed."

cache_miss_reason 全表（官方口径，值得存起来）

> "The response reports the earliest divergence only, so fix it first; later ones may be hidden behind it."

类型 含义 怎么改
model_changed 换了模型（路由/AB/降级触发）。缓存是按模型分的 一段缓存会话里模型保持不变
system_changed system 变了，通常是把时间戳/请求 ID 插进了系统提示词 系统提示词做成逐字节稳定的常量，动态数据挪到断点后的第一条 user 消息
tools_changed tools 数组增删、重排，或 schema JSON 序列化不确定 每轮发同样的工具、同样的顺序、排序过的 key
messages_changed 前三者都没变，但历史被改写/截断/重排了，而不是追加 把历史当成 append-only，assistant content 和 tool_result 原样回传
previous_message_not_found 找不到上一条的指纹。这不代表你的请求变了 每轮都带 beta header，相邻轮次别隔太久
unavailable 另一个「影响提示词的参数」变了：tool_choice、thinking、context_management、output_config、output_format、或活跃的 beta header 集合 这些参数在一段缓存会话的生命周期内保持不变

最容易被忽略的是最后一行。 很多人排查半天 system 和 tools，其实是 thinking 配置或者 beta header 集合变了。

诊断结果 × 实际命中率的四象限

官方给的这张交叉表比单看任何一个指标都准：

diagnostics 缓存读取 token 结论
null 高 ✅ 正常，前缀稳定且命中
null 低/零 请求没变，是缓存条目过期了 → 缩短轮次间隔，或用 1 小时 TTL
*_changed 低/零 ❌ 你的 bug，按 type 修
*_changed 高 罕见：变化发生在靠后位置，但更早的 cache_control 断点仍命中。值得修，影响小

📌 对应到 Claude Code 用户： 你不需要写 API 代码就能用上——/cost 和状态栏 prompt_cache 字段现在就是这套诊断的 CLI 版本。把 prompt_cache 加进你的 statusline。

今日焦点三：两个真实的权限绕过修复 —— 如果你依赖「只读目录」，请立刻升级

2.1.260 里有两条修复不是体验问题，是安全边界失效：

> "Fixed Edit/Write/Read permission rules whose path contains parentheses being dropped as invalid or ignored by the Bash sandbox, which left "read-only" folders writable."

> "Fixed Bash permission checks auto-approving zsh commands that hide a command substitution in a REPORTTIME, REPORTMEMORY or DIRSTACKSIZE assignment; these now prompt for approval."

第一条影响面很实际：macOS 上带括号的路径极其常见（~/Library/Application Support/…、项目 (备份)/、Photos (2026)/）。你以为设了 Read(./data (raw)/) 的只读保护，实际上这条规则被整个丢掉了。**

还有一条相关的：

> "Fixed one file permission rule with an uncompilable pattern (e.g. an unclosed [) making every file edit fail with Invalid regular expression."

一条写错的规则会让整个权限系统失效——一个方向是全部报错，另一个方向是静默放行。两种都很糟。

以及一条回滚，说明官方也在这块反复权衡：

> "Reverted the 2.1.259 change applying Read() deny rules to Bash arguments; it denied npm run build under a Read(.//build/) rule in every mode and made cd … && grep prompt even in auto mode."

📌 今天就能做的一件事： 打开你的 settings.json，检查所有 Read() / Edit() / Write() 规则里有没有括号或方括号。有的话，升级到 2.1.260 之后重新验证一遍这些规则是否真的生效。2.1.260 还改进了报错：像 Edit(C:\dir\(name)\**) 这种 \( 被当成转义括号而非路径分隔符的写法，现在会提示你换一种无歧义的写法。

今日焦点四：--permission-prompts none —— 这份报告自己就是它的用例

2.1.259 加了一个专为无人值守场景设计的开关：

> "Added --permission-prompts none for unattended headless hosts: anything that would prompt is denied automatically while the active permission mode (including auto mode) keeps deciding."

为什么这条对本报告特别有意义： 你正在读的这份日报连续六期无法采集 X / YouTube 一手数据，原因就是——定时任务在无人值守时跑，浏览器站点权限需要人点「批准」，没人在，于是卡住。--permission-prompts none 把这个含糊状态变成了确定行为：该问的一律判定为拒绝，不挂起、不假装成功。

这是一个值得记住的工程原则：无人值守环境下，「等待批准」是最差的语义。要么预授权，要么明确拒绝并让任务如实报告「这块没拿到」——像本报告第三、五节留空互动量那样。

一、高级用法精选（按难度分层）

Level 1 — 基础配置

  • claude --version 应该是你今天的第一条命令。 低于 2.1.260 且在用 Fable 5.1，你正在为一个已修复的缓存 bug 付钱
  • 原生安装包瘦身：2.1.259 用 zstd 压缩，Linux x64 的安装/自动更新下载从 约 340MB 降到约 75MB
  • /diff 新面板（2.1.260）：全屏模式下在对话旁边开一栏，Claude 编辑时实时显示未提交改动。用 /diff 切换
  • ctrl+l / cmd+k（2.1.260）：全屏模式下现在像终端 clear 一样清空 transcript 视图，往上滚仍能看到历史
  • timeFormat / timeZone（2.1.257）：12 小时 / 24 小时 / 24 小时 UTC / 自定义 strftime

Level 2 — Skills 技巧

  • 9/2 官方三分之一定律（昨日焦点，今天仍是最高杠杆的一条）：≥1/3 的会话会用到 → 放系统提示词；<1/3 → 放 skill。 安全/法务/品牌约束无论比例多低都常驻
  • skill 加载要花一个模型轮次（"Loading a skill costs a model turn"）。如果这个 skill 是从已知信号可预测的，直接在提示词里注入内容，跳过那一轮
  • skillOverrides 别名修复（2.1.260）：以别名为 key 的托管覆盖（如用 checkup 指 /doctor）此前不生效；Skill(name) 拒绝规则现在也覆盖 :name 形式的嵌套 skill
  • frontmatter model: 修复（2.1.259）：自定义命令和 skill 的 model: 在交互式会话中此前被忽略

Level 3 — 定时任务

  • --permission-prompts none（2.1.259）：无人值守 headless 的正确姿势，见今日焦点四
  • /schedule 空跑修复（2.1.257）：保存时缺少 message role 的定时任务会「跑起来但什么都不做」
  • 暂停会话的审批修复（2.1.259）：远程和定时会话在暂停期间被批准 connector 工具权限后，此前会卡住不动
  • claude -p 提前退出修复（2.1.257）：-p 此前在最终结果后约 5 秒退出，会掐死模型刚布置的 Monitor；现在会等它触发或超时

Level 4 — Connectors & MCP

  • managedMcpServers（2.1.259，企业级）：组织可以给每个用户下发 HTTP/SSE MCP 服务器，条目格式与 .mcp.json 相同；指定本地命令的条目会被跳过
  • allowedMcpServers 语义变更（2.1.259）：现在只管用户自己添加的服务器。升级后，你的允许列表原本过滤掉的 managed-mcp.json 服务器会重新加载——要挡住请改用 deniedMcpServers。⚠️ 这是一条会在升级时静默改变行为的变更
  • MCP 启动错误可见性（2.1.259）：在列举工具时断开的 MCP 服务器，此前显示为「已连接但零工具」，现在如实报错

Level 5 — Hooks 自动化控制

  • 托管 CLAUDE.md 不再触发安全审批弹窗（2.1.260）——但 hooks、shell 命令、sandbox、不安全的 env 设置仍然需要审批。这条边界划得很清楚：注入知识 vs 注入执行能力
  • 符号链接逃逸修复（2.1.257）：插件此前能通过 command / agent / skill / hooks 组件路径上的符号链接读到自己目录之外的文件，现在直接拒绝
  • Stop hook 的隐藏代价修复（2.1.259）：阻断型 Stop hook 会让被阻断那一轮丢失模型的推理内容，并在部分模型上丢失缓存命中
  • permissions.ask 绕过修复（2.1.257）：匹配命令跑在复合命令或子 shell 里时，auto 模式下会跳过确认提示

Level 6 — 子代理编排

  • 后台命令 1 小时上限被移除（2.1.260）：子代理启动的后台命令现在跑到退出或被停止为止，与主会话一致
  • 嵌套后台子代理结果落盘（2.1.259）：结果保存进父子代理的 transcript，恢复的子代理能保留它们
  • SendMessage 唤醒修复（2.1.260）：通过 SendMessage 恢复另一个 agent 的子代理，此前永远不会被那个 agent 的完成唤醒（通知错发到主对话）
  • 子代理断流自动续跑（2.1.257）：因电脑休眠、断连或服务端错误被截断时自动继续，不再以残缺响应收尾
  • CLAUDE_CODE_SUBAGENT_MODEL_FORCE（2.1.257）：强制所有子代理用同一模型，忽略每次 spawn 和 agent 定义里的模型覆盖
  • agent teams transcript 修复（2.1.260）：长时间 API 重试等待期间，重试提示会挤掉真实消息导致 transcript 变空
  • ⚠️ 但记住 9/2 官方那条相反的结论： 子代理是上下文隔离工具，不是任务拆分工具。"Every handoff to a subagent is a state-lossy operation."

Level 7 — 专家级工作流

  • 1M 上下文自动压缩（2.1.260）：Opus 和 Fable 会话现在在逼近 1M 上限前压缩；超大上下文的恢复性压缩不再在 10 分钟超时
  • Containment Escape 规则（2.1.257）：auto 模式下，云元数据凭据获取、出网规避、跨租户访问不再自动批准，除非你的环境标记为预期行为。背景见 How we built Claude Code auto mode
  • blockReadsOutsideWorkingDirectories（2.1.257 引入 / 2.1.260 修复）：首次读取工作目录外文件时一次性询问。2.1.260 修了 macOS 上它把用户 git config 对沙箱 git 藏起来、以及藏掉 worktree 隔离子代理自己的 checkout 的问题
  • /ultrareview 等待上限从 30 分钟提到 45 分钟（2.1.260）
  • Workflow 结构化输出（2.1.260）：agent({schema}) 会提前拒绝永远无法满足的 JSON Schema；重试上限错误现在带上最后一次校验失败详情
  • /rewind 两处修复（2.1.260）：检查点备份文件缺失时此前谎报成功；rewind 之后残留的文件读取追踪会导致「File unchanged since last read」空存根和整文件重新注入
