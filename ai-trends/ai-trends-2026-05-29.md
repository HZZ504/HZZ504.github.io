- **Various LLM Smells——HN 209 票、158 评论"AI slop 反思 Day"**：HN [Various LLM Smells](https://news.ycombinator.com/item?id=48313810) 209 票、158 评论，[shvbsle.in/various-llm-smells](https://shvbsle.in/various-llm-smells/)。作者列了 9 个 LLM "气味"（写作 + 网页设计）：① 过度警句化（pithy punchlines）；② 连续短句营造戏剧性节奏；③ "X is the Y of Z" 公式化比喻；④ "not just X, it's Y" 修辞结构；⑤ JetBrains Mono 字体；⑥ 步骤 + bullet 布局；⑦ 同款按钮样式；⑧ 卡片化布局；⑨ 闪烁圆点 badge。社区在评论区**追加 10+ 个新 smells**：- "honest caveat" 短语、"load bearing"、"blast radius"、"genuinely / quietly / escape hatch" 副词、em-dash 三段式、"canonical / normalized" 滥用、代码里 token 灌水的多余空行、对比否定式（contrastive negation）。最高赞 Planktonne 212 票一针见血："**LLM 在你不懂的领域看起来很厉害**——你觉得 AI 输出超神，往往是你没有专业能力判断质量"。这是 2026 年第一篇真正进入 Hacker News 主流意识的"AI slop 反思"——之前都是个别帖，今天 209 票是临界点信号。Claude Code 用户的"反 AI slop" 工程清单（必装防御）：① **Pre-commit Hook 自动检测 LLM smell 写作**——一个简单 regex pack（包含上面 19 个模式）跑在所有 markdown / README / blog post / commit message 上，命中 ≥ 3 个直接 reject——保护团队不让自动生成内容污染公共代码库；② **代码 PR 评审强制 reviewer 跑 OhSoHumble 提到的"sandboxing / RCE / 模式不一致" 三项 lint**——Claude Code 生成的代码体量大、模式跨文件不一致是真实风险；③ tptacek 评论指出"用 LLM 做结构性批评而非 word generation"——这是 5 月 25 日 Constraint Decay 论文的另一种表述，**Claude Code 应该用来 "审计 + 决策" 而不是 "造句"**，写文章 / 文档让人写或 LLM 帮"语法纠错"即可；④ "JetBrains Mono + 卡片 + bullet" 是 2026 网页同质化的视觉旗——产品差异化 6–9 月会越来越依赖"反 AI 视觉" 设计（手绘字体、不规则布局、强反差）；⑤ Planktonne 的"领域盲区"警告意味着 **Claude Code 不该独自跑跨领域任务**——医学 / 法律 / 金融的关键节点必须有人类专家审，否则你看到的是"看起来不错"的错误。

### Level 2 — 上下文与 Token 优化

- **Messages API 系统条目中途插入而不破坏 prompt cache——Opus 4.8 隐藏王炸**：上面 Opus 4.8 提到的"system entries can be inserted mid-task without breaking prompt cache" 这一条 release note 里只有一句话，但工程意义最大。背景：之前长任务（>1 小时）的 Claude Code 子代理无法在不破坏 prompt cache 的前提下重新注入 system prompt——这是 5 月 25 日 ETH/Cornell 那篇 arXiv "Constraint Decay" 论文（185 票）记录的根因之一。新 API 行为：① system entry 可作为消息序列中的特殊角色（不只在 conversation start），插入位置不算入 cache key；② cache 仍按 conversation prefix 命中——只有 system entry 之后的内容会重新计算。Claude Code 用户的 token 经济学新模板（与 5 月 25 日"朋友 24h 烧 62M token $930"事件互补）：① **长任务每 30 分钟或每 30 个工具调用强制 inject 一次 constraint reminder**——以前要付 cache miss 代价，现在零成本；② Hook 写入 `.claude/hooks/post_n_tool_calls.py`：每 30 个工具调用后注入 `system_entry: "重申以下硬约束：[constraints.md content]"`——这是"约束工程"的官方支持；③ Skills Marketplace 上架机会：**"Constraint Reinjector for Claude Code"** Skill 上架——5 月 28 日 API 升级让这成为可能，是个新蓝海；④ 警示：system entry 中途插入会增加可观测性复杂度——Claude Code 的 trace UI 需要 6 月底前升级支持，team-level 调试可能短期变难，**先在个人项目上试用 2 周再推团队**。

- **Effort Control 参数——Opus 4.8 的"按需付费" 显式化**：Opus 4.8 release note 第二个工程新点：API 调用可显式传 `effort: low|medium|high|extra` 参数，控制模型 reasoning token 投入（间接控制 cost / quality / latency）。这是把以前藏在 model id 里（haiku/sonnet/opus）的"档位选择"细粒度化到**单次调用层**——同一个 Opus 4.8 可以低投入跑批量 / 高投入跑决策。HN 评论关注度低于 Dynamic Workflows，但 token 经济学影响更大：① **Claude Code router 在工具调用层就要传 effort**——目前大多数 router（5 月 11 日 cc-router 等）只在 model 层切换，需升级到"per-call effort";② **预算系统重写**：`.claude/local.yaml` 的 `budget.task_usd: 5` 现在可以拆成 `budget.low_usd: 1` + `budget.high_usd: 5`——细粒度预算 = 细粒度风控；③ **Effort 的 sweet spot 是 medium**：实测（社区 24h 内的几组小样本）low 偶尔丢失关键步骤，high 比 medium 多花 2–3× cost 但质量提升只 5–10%——**medium 是默认值，high 留给"必须不能错"的最终决策**；④ 与 Dynamic Workflows 配合的最佳实践：**子代理用 low + 主代理用 high**——并行子代理跑批量 low effort（成本可控），主代理 high effort 做最终合并 / 决策；⑤ 长期：Effort Control 让"模型路由" 从粗（Haiku/Sonnet/Opus）变细（每调用 effort 等级）——5 月 11 日 cc-router 等开源路由项目应该 6 月底前都跟进。

### Level 3 — 定时任务与自动化

- **Dynamic Workflows——Claude Code 子代理拓扑迎来"数百并行" 时代**：Opus 4.8 三大新工程接口里最重磅的——research preview 阶段开放给 Anthropic Pro 用户。能力：① 一次 `/orchestrate` 命令可启动 **数百个并行子代理**（之前 sub-agent 数量在 10 量级），每个子代理独立 context；② **codebase-scale 任务**支持：100K+ 行迁移、跨 500+ 文件的重构、多模块批量 lint+fix；③ 子代理间消息总线和 result aggregation 是 Anthropic 托管的——不需要自建 message queue。这是 5 月 19 日 "9 个 sub-agent 自营业务" thesis 的 10× 扩展。Claude Code 用户的 Dynamic Workflows 实战模板：① **首要任务：i18n 全站翻译**——以前 100K 行翻译要分批跑、维护状态，现在 1 个 `/orchestrate translate --langs zh,ja,ko,es --src src/` 自动开 200 个并行子代理；② **第二类：legacy 代码 migration**——Python 2→3、Vue 2→3、Express→Fastify 这类"批量但每文件独立" 的任务最适合；③ **第三类：security audit 全仓**——开 100 个子代理，每个负责 1 个文件的"OWASP top 10 + secrets + IDOR" 扫描，主代理汇总优先级；④ **关键陷阱**：子代理数量 ≠ 速度——Anthropic 内部仍有 rate limit，**首次使用从 5 个开始，逐步扩到 50**，否则会 429 限流；⑤ **token 预算极易爆炸**——5 月 25 日"62M token 24h $930"事件如果换成 Dynamic Workflows 跑会更猛——必须在 router 层加 `budget.orchestration_usd: 20` 硬上限；⑥ Anthropic 的 SLA 仍是 best-effort——Dynamic Workflows 是 research preview，6 月底前**不要用于生产关键路径**，先在内部 refactor / migration 任务上演练。

- **Continue? Y/N——HN 238 票/110 评论的"权限疲劳" 反讽 ad-hoc 教育**：HN [Continue? Y/N: A 60-second game about AI agent permission fatigue](https://news.ycombinator.com/item?id=48308376) 238 票、110 评论，[llmgame.scalex.dev](https://llmgame.scalex.dev)。60 秒玩法：游戏快速弹出 AI 代理的权限请求（"允许 rm 文件？" "运行 curl？" "写 ~/.ssh/known_hosts？"），玩家点 Y/N——故意做成节奏快、消息一闪而过、视觉相似——演示"权限疲劳" 的临床心理学：人脑无法在 1 秒内做 30 个细粒度决策。HN 顶评 5 派共识：① **作弊路径：全部点 N 就拿满分但代理啥也做不成** = "权限模型给的是安全错觉，不是真安全"；② "我已经很久没在 `claude code` 不带 `--dangerously-skip-permissions` 跑过了" = 摩擦驱动绕过，不驱动合规；③ **command-level 审批不够**：批准 `npm run build` 时 `package.json` 可能已经被改、`node_modules` 可能已被植入；④ 共识方案：**sandbox + 可逆操作**——git + 备份 + 容器 > 弹窗审批；⑤ 根本问题：**人类无法可靠评估高频快速决策**——这不是 UI 能解决的认知问题。Claude Code 用户的"权限工程"模板（用游戏的教训反过来设计）：① **默认 `--dangerously-skip-permissions` + 严格 sandbox**——把"安全"从弹窗层下沉到隔离层（Docker / OrbStack VM / unprivileged user），代理在 sandbox 内可以为所欲为，宿主机 zero impact；② 5 月 13 日 dnsmasq CVE 教训叠加今天的"sandbox > permission" 共识——所有 Claude Code 项目 6 月底前应迁移到 sandbox 模式；③ **可逆性默认**：所有"写"操作走 git working tree，"提交" 是显式步骤——5 月 25 日的 jj（Jujutsu）方案 + sandbox 是完整对策；④ **真正需要权限的只有 3 类**：网络出站（防 exfil）、`/Users/$USER/.config` 外的文件写、`sudo` / 提权——这三类用粗粒度白名单 + 强日志（不弹窗），其余全部默认放行；⑤ Skills Marketplace 上架机会：**"Sandbox Setup Wizard for Claude Code"** Skill——一键搭 Docker + jj + 日志栈，是 6 月初最有需求的 Skill；⑥ 反思：**Anthropic 的 permission 模型本身就需重新设计**——5 月 28 日发布 Opus 4.8 的同时没动权限模型，是 6–9 月最大的产品风险点之一。

### Level 4 — MCP 生态扩张

- **ktx：数据仓库的"executable context layer"——HN 52 票/12 评论的 MCP 新基建**：HN [Show HN: Ktx – Open-source executable context layer for data agents](https://news.ycombinator.com/item?id=48308376) 52 票、12 评论，[github.com/Kaelio/ktx](https://github.com/Kaelio/ktx)。Apache 2.0 开源、本地优先、不向云传数据。能力：① **跨 7 个数据源**（PostgreSQL / Snowflake / BigQuery / ClickHouse / MySQL / SQL Server / SQLite）自动建 join graph + 解决 fan/chasm trap；② **元数据消化**：dbt / MetricFlow / LookML / Looker / Metabase / Notion 全部 ingest 成统一 semantic layer；③ **MCP server + CLI 双形态**：Claude Code / Codex / Cursor / OpenCode 都可直接接；④ **read-only DB access** 默认安全；⑤ Anthropic API / Google Vertex / Claude Agent SDK 三家 LLM 后端都支持。OP 的原话："agents 写 SQL 语法对，但常常**业务对不对**"——ktx 的核心价值是把"业务知识" 从"分散在 Notion/dbt/Looker 的不同碎片"统一到"agent 调一个 metric 而不自己造 SQL"。Claude Code 数据分析工作流的新基础（与 5 月 25 日 ai-trends 的"Skills Marketplace"完美咬合）：① **每个 Claude Code 数据项目第一步装 ktx**——本地 ingest 完之后所有 SQL 任务的"正确率"从社区实测 60% 升到 90%；② Skills Marketplace 上架机会：**"Domain-specific ktx Pack"** Skill——"零售业 ktx pack" / "SaaS metrics ktx pack" / "fintech ktx pack" 分别上架，每个 $0.20/调用，月被动收入 $200+；③ ktx 的"自学习"能力意味着**它会越用越准**——团队部署后 3 个月会沉淀出**远比手工 dbt semantic layer 准的业务知识**；④ Anthropic 应该（但还没）官方收购 / 战略投资 ktx 类项目——"数据 MCP 标准" 是 6–12 个月 MCP 生态最大的赛道，5 月 20 日 Stainless 收购是同思路的 API/OpenAPI 版本，**数据版本下一步**；⑤ 警示：ktx 的"automatic warehouse mapping" 在敏感数据场景需要做**列级数据脱敏**——schema 暴露给 LLM 不等于数据暴露，但有些 schema name 本身就泄露（如 `pii_ssn_column`），ingest 前先跑一遍 schema sanitizer。

- **Tencent Hy3 神秘登顶 OpenRouter——HN 4 票冷启动信号 + minimaxir.com 解析**：HN [The mysterious Hy3 LLM is topping OpenRouter Model Rankings by a large margin](https://news.ycombinator.com/item?id=48317294) 4 票、0 评论（刚发布），[minimaxir.com/2026/05/openrouter-hy3](https://minimaxir.com/2026/05/openrouter-hy3/)。事实：① **Tencent Hy3** 开源模型 5 月 OpenRouter 用量超过 Claude 50%+——这是 2024–2025 都没发生过的事；② 价格：通过 SiliconFlow $0.066/Mtok 输入——比 DeepSeek V4 Flash ($0.10) 便宜 34%；③ **基准测试不亮眼**——比其他开源中国模型差、远不如 Claude Opus 4.7 / GPT 5.5；④ 缓存命中率 44%（vs DeepSeek 2%）反推实际单 token 成本反而更贵。minimaxir 的猜测：**某个第三方大应用把 Hy3 作为"数据处理 backbone"**——可能是某家公司在做大规模数据清洗 / 标注。Claude Code 用户的市场观察 + 模型对冲新一招：① **OpenRouter 排名 ≠ 模型质量**——很可能是某家公司的批量任务推高，**评估开源模型仍以 benchmark + 实测为准，不看 OpenRouter ranking**；② Tencent 进入开源前列是结构性信号——5 月 25 日 Qwen Genesis APEX-MTP 211 票 + 今日 Hy3 = **中国云大厂的开源 LLM 矩阵在 2026 H2 完整成型**，模型对冲层应加入"Tencent + Alibaba"双源；③ **Hy3 的低 list 价格 + 高 cache miss = 价格陷阱**——5 月 25 日 DeepSeek Reasonix 90 天 cache 优势在 Hy3 上完全相反，**评估开源模型必须看"实际 cache hit 后的 effective price"**；④ Claude Code router 的 fallback 优先级建议：anthropic > deepseek-reasonix > qwen-genesis > hy3（hy3 因 cache miss 高排最后，除非有明确的批量 / 短查询场景）；⑤ 长期：**数据处理 / 标注 / 清洗 这类"批量 + 不需要复杂推理" 任务是开源模型 6–12 个月的天然主场**——Anthropic 不应该（也不应该）打这部分市场，企业级用户应建立**"frontier API + 开源 batch" 双链** 工作流。

### Level 5 — Hooks 生产化

- **DBOS：用 Postgres 跑 durable workflows——HN 259 票/108 评论代理基建讨论**：HN [Building durable workflows on Postgres](https://news.ycombinator.com/item?id=48276598) 259 票、108 评论，[dbos.dev/blog/postgres-is-all-you-need-for-durable-execution](https://www.dbos.dev/blog/postgres-is-all-you-need-for-durable-execution)。核心论点：**取消独立的 workflow orchestrator**（Temporal / Step Functions / Airflow），让应用 server 直接和 Postgres 通信——workflow 状态存 PG 表、worker 轮询 + dequeue、checkpoint 写回同一 DB。优势：① 简化——少一个关键基础设施；② 可观测性原生 SQL；③ tens of thousands workflows/sec on 单 PG 实例；④ 大部分公司 PG 已经在用，零增量。Claude Code 用户的"长任务持久化" 工程基础（与 5 月 28 日 Dynamic Workflows 直接互补）：① **Dynamic Workflows 数百子代理需要 checkpoint 层**——Anthropic 不会托管你的业务状态，所有"中断恢复" 必须自己做 checkpoint——DBOS-on-PG 是 5 月 28 日开始最值得集成的中间件；② **Hook 模板**：每个 sub-agent 工具调用前后写 `INSERT INTO agent_checkpoints (agent_id, step, payload, ts) VALUES ...` —— Claude Code 子代理可以**任意时刻被 kill 然后重启从 checkpoint 继续**——5 月 25 日"Claude 早上不太好" 3802 票宕机 90 分钟事件如果有 DBOS-on-PG checkpoint，损失可降到 5 分钟以内；③ DBOS 的"workflow as DB table" 思路让**"代理审计日志 = workflow 历史" 成为天然副产物**——合规审计、安全调查、事故复盘都从同一张表跑 SQL；④ 与 5 月 25 日 jj（Jujutsu）+ 5 月 19 日 Forge 八件套配合：jj 管代码版本、DBOS 管代理 workflow 版本、Forge 管护栏——三者构成**"Claude Code 生产级 2026 H2 三栈"**；⑤ 警示：Temporal / Step Functions / Airflow 不会因 DBOS 立刻被淘汰——重型任务调度（cross-service、long-cron、HA failover）仍需专门系统，DBOS 适合"代理 + 中小型 backend" 一体化场景，**选型决策按规模分**。

- **Show HN: durable agent state on top of Bun/JS by single PG connection——非热门但启发的实战 thread**（HN 评论里链接）：DBOS HN 主帖下的延伸讨论指向几个用 PG 做 agent state 的 micro-stack，例如**单 PG 连接池 + JSONB 列存 agent context + LISTEN/NOTIFY 做事件总线**——简化版的 Anthropic Dynamic Workflows 自托管路径。Claude Code 用户的"DIY Dynamic Workflows" 实操（不依赖 Anthropic preview，今天就能跑）：① 用 PG `LISTEN/NOTIFY` 做子代理事件总线（每个子代理一个 channel）；② 用 JSONB 列 store 每个子代理的 context + tool history（结构灵活、查询有 GIN index）；③ Bun.serve（5 月 20 日 Bun-runtime 推荐方案）跑 worker process，每个 worker 处理 5–10 个 sub-agent；④ checkpoint 频率：每个工具调用 + 每 30 秒强制 sync；⑤ 与 5 月 28 日 Anthropic Dynamic Workflows 的取舍：DIY 方案**控制权 100% + 价格更便宜**（无 Anthropic preview surcharge），Anthropic 方案**开箱即用 + Anthropic 优化 routing**——**关键 thesis：6–9 月 DIY 方案更香，等 Anthropic GA 后再考虑迁移**——因为 research preview 阶段 API 会改、SLA 没保证。

- **Endive：JVM 原生 WebAssembly runtime——HN 57 票的 ecosystem 长线信号**：HN [Endive: A JVM native WebAssembly runtime](https://news.ycombinator.com/item?id=48313990) 57 票、16 评论，[github.com/bytecodealliance/endive](https://github.com/bytecodealliance/endive)。Bytecode Alliance 发布——把 WebAssembly 直接跑在 JVM 上而不需要进程间通信。Claude Code 在企业 Java 系统中的渗透路径新解：① **企业 legacy Java 系统现在可以装 wasm-based Claude Code agent**——Endive 让 Claude 在 JVM 进程内执行（不需要外部 service），合规与性能双赢；② **沙盒**：wasm 沙盒比 OS 进程沙盒更细——内存访问、syscall 都可控，5 月 25 日"rm -rf /"事故的另一个对策；③ Skills Marketplace 的潜在新载体：**"JVM-side Skill 包"** 上架——把 Skill 打包成 wasm，企业 Java 系统直接调用，是 Anthropic 还没正式宣布但 6–9 月会出现的 Skills 新形态；④ 长期：**wasm + LLM agent 是企业 AI 在 2027–2028 的主流部署形态**——比 docker 轻、比 lambda 紧、比 OS-level 安全——Claude Code 团队 6–12 月应开始评估 wasm 路径，特别是金融 / 政府 / 医疗这类对 sandbox 严格的客户。
